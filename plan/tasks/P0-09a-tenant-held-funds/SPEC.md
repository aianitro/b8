# P0-09a-tenant-held-funds — tenant-held funds reduce net worth correctly
**Roadmap item:** ROADMAP.md §5 Phase 0 (truthful domain model), addendum to step 9 (per-property P&L / ledger) — `plan/tasks/P0-09a-tenant-held-funds/ITEM.md`
**Status:** FROZEN@G0 (2026-08-27; draft 3 — see `GATES.md` G0 reviews 1–3)
**Author:** spec-writer

## Goal
A rental property gains two new, independently-visible figures on its detail page: the **security deposit currently held** and the **last month's rent currently held**, each resolved from its own append-only, manually-entered observation series — the same "enter a reading, latest wins" motif `property_valuations` already uses for market value. Only the security-deposit figure participates in net worth: `computeNetWorthBreakdown`'s `liabilities` component (and therefore `total`) is reduced by exactly the sum of currently-recorded security deposits across properties, while `operational`, `capitalFinancial`, and `realEstateEquity` are unaffected, and the four components still sum to `total` exactly. A deposit counts **regardless of whether its property currently has a recorded valuation** — deliberately unlike a linked mortgage, which is dropped together with an unvalued property (see Conventions and Failure modes for why the two rules differ). Every dollar a deposit removes from `liabilities` is also represented by a matching `NetWorthContribution` (see "Conventions — Contributions" below), so `/net-worth`'s per-line breakdown for "Other debt" continues to sum to that card's own headline figure — the whole reason the `contributions[]` array exists. The same component's static caption is corrected so it stays true once a deposit can appear there: "Other debt" is no longer described as exclusively "Loans not secured against a property," which becomes a false description of a security deposit — a debt that *is* tied to a specific property and is not a loan at all. The last-month-rent-held figure is displayed identically alongside the deposit but contributes to **no** net-worth component and emits **no** contribution — per the owner's decision recorded in `ITEM.md`, it remains the owner's already-recognized cash-basis income, not a liability. A property that has never had either figure entered is distinguishable, in the data and on screen, from one with an entered `$0`: the former resolves to `null` and renders as "—"; the latter is a real reading and renders as `$0`. Neither `computePropertyPnl` nor `buildPropertyLedger` changes — the ledger keeps reconciling the account's actual cash movements (including the transactions that brought the deposit or last-month cash in) exactly as it does today; the two new figures are a net-worth-level and disclosure-level fact layered on top, not a rewrite of the cash record. The data-entry affordance for both figures appears only for `type = 'rental'` properties.

## Non-goals
- No change to `lib/domain/propertyPnl.ts`. How a security-deposit-received transaction is categorized (income, transfer, or otherwise) is unchanged; this task does not reclassify it.
- No change to `lib/domain/propertyLedger.ts`. `buildPropertyLedger`'s beginning balance, per-row running balance, and ending balance are computed exactly as today. The deposit/last-month figures are never subtracted from or added to it.
- No automatic derivation of either figure from transaction history (e.g. summing transactions in a "Security Deposit" category). Both are manually entered observations, entered through the property UI like a market valuation — never computed from `transactions`.
- No backfill or historical rewrite of existing `net_worth_snapshots` rows. Rows already written keep whatever figure they already hold; this task changes only what *future* writes compute.
- **No extension to the `/properties` summary list.** The two figures, and their display, are scoped to the property detail page (`app/properties/[id]/page.tsx`) only. This is a decided boundary, not implementer discretion — a diff touching `app/properties/page.tsx` for this purpose is out of scope.
- **No data-entry affordance on `type = 'primary'` properties.** The UI offers entry of either figure only on `type = 'rental'` properties. (The pure domain functions that compute net worth and resolve the display value remain type-agnostic — see Conventions and Failure modes — this is a UI-level scope boundary, not a domain-layer constraint, and the two must not be conflated.)
- No itemizing of multiple tenants/leases per property. Each figure is a single current total per property, not a per-lease breakdown.
- No new gating by `hidden` or `exclude_from_budget`. Those flags govern transactions and budget categories; the new observation series has neither, and must not be made to depend on either.
- No landscape (`operational`/`capital`) split introduced for either figure — the `liabilities` component they feed is already a single, landscape-agnostic component today.
- No new authentication, API versioning, or caching layer.
- No live-rendered screenshot or dev-database evidence (see "Evidence required").
- **`app/net-worth/page.tsx` is in scope for exactly one narrow edit, and no other.** The only permitted change to this file is a minimal, in-place text edit to the `liabilities` entry's `hint` (and, at the implementer's discretion, `label`) inside the existing `COMPONENTS` array, so the static description stops being false once a security-deposit contribution can appear in that component (see BLOCK G0-5 in `GATES.md` "G0 review 2," resolved below under Conventions). Everything else in that file is out of scope: its generic per-line `kind`/`id` resolution (lines 96–101, already verified correct and requiring no change), its `href` values — including the `liabilities` card's `href: '/accounts'`, which is deliberately left as-is (see Conventions) — its layout, and every other component's metadata.

## Conventions this task must honor
- **Sign:** Both the security-deposit-held and last-month-rent-held figures are recorded as **positive magnitudes** — identical convention to `account_valuations.value`/`property_valuations.value` ("always a positive magnitude; sign is derived from usage, not stored"). The security deposit's contribution to the `liabilities` component is its **negation**, mirroring the existing line `liabilities -= magnitude` that `computeNetWorthBreakdown` already applies to an unlinked valuation-mode liability account's positive value. The last-month-rent-held figure is **never negated into, or otherwise arithmetically combined with, any of the four net-worth components** — it has no sign-bearing role in net worth at all.
- **Unvalued-property rule — deliberately NOT the mortgage rule:** a property's linked mortgage is dropped together with the property when the property has no recorded valuation, because the mortgage is netted **against** that value inside `realEstateEquity`, and a naked mortgage with no value to offset it would read as a wildly negative, misleading equity. A security deposit is netted against **nothing** — it is an independent obligation to a tenant, owed in full whether or not the house has been revalued this quarter. **A recorded security deposit therefore reduces `liabilities` unconditionally, regardless of whether its property appears in `unvaluedPropertyIds`.** The deposit-processing step must not consult `unvaluedPropertyIds`, the `excluded` set, or any property-valuation input at all — it is a function of the deposit observation alone. A property's continued presence in `unvaluedPropertyIds` for equity-disclosure purposes is unaffected either way; the two facts (equity unknown vs. deposit owed) are independent and both remain true simultaneously.
- **Contributions (correctness, not styling):** whenever a property has a recorded security-deposit observation (including an explicit `$0`), `computeNetWorthBreakdown` must emit exactly one matching `NetWorthContribution` with `component: 'liabilities'`, `value` equal to the negated deposit magnitude, `kind: 'property'`, `id: String(propertyId)` — and this happens **unconditionally**, per the unvalued-property rule above, even for a property with no other contribution of any kind. **`propertyId` on this contribution stays `null`** — the existing doc comment on `NetWorthContribution.propertyId` states it is set "only within realEstateEquity... Null everywhere else," and `groupRealEstateEquity` already only inspects contributions where `component === 'realEstateEquity'`, so a non-null `propertyId` here would add nothing functionally while breaking a documented invariant a future reader relies on. Entity identity for this line flows through `kind` + `id` alone, exactly like every other non-realEstateEquity contribution already does. This shape is not incidental: `app/net-worth/page.tsx`'s existing generic per-line resolution (`kind === 'property'` ⇒ resolve the display name from the properties table, link to `/properties/{id}`) already handles a `kind: 'property'` line correctly in *any* component, including `liabilities`, with no change to that mapping logic required — `getLabels()` (line 41) selects every property unconditionally, so the name resolves even for a property absent from `realEstateEquity` entirely. A property with no deposit observation at all emits no contribution, exactly as an unvalued property today is excluded from `contributions` entirely. The last-month-rent-held figure never emits a contribution of any kind, anywhere.
- **Caption accuracy (the one permitted edit to `app/net-worth/page.tsx`):** the `liabilities` component's `hint` — currently the unqualified string `'Loans not secured against a property'` — becomes false the moment a security-deposit contribution can land in this component: a deposit is not a loan, and it *is* tied to a specific property. The `hint` (and, optionally, `label`) for the `key: 'liabilities'` entry in the `COMPONENTS` array must be edited so it remains an accurate description of everything that can appear in the component, including a security-deposit line — concretely, the edited text must mention "deposit" (case-insensitive) so the omission is checkable (see acceptance #11). The `label` `'Other debt'` is left as-is — a held deposit is a form of debt, so the label is not false; only the `hint` is required to change. The component tile's `href` (`'/accounts'`) is **deliberately left unchanged** — it remains a reasonable generic entry point since unlinked liability accounts remain the dominant content of this component, and the per-line link on the deposit's own contribution row (already `/properties/{id}`, verified correct) is what a reader actually follows to reach that specific property. This is a decided choice, not an oversight.
- **Rounding:** Both figures are entered and stored to the cent (`NUMERIC(14,2)`, matching `account_valuations`/`property_valuations`). They are combined into `liabilities`/`total` as-is, without re-rounding — the same "already cent-precise, sum directly" treatment `computeNetWorthBreakdown` already gives every other magnitude it totals. This is a single point-in-time reading being subtracted once, not an accumulation across steps, so there is no "per step vs. once at the end" ambiguity to resolve — one subtraction, one place.
- **Landscape + exclusions:** Neither figure is scoped to `operational` vs. `capital` — the `liabilities` component itself is a single, landscape-agnostic component today, and this task does not change that. Neither `hidden` (a `transactions` flag) nor `exclude_from_budget` (a `budget_categories` flag) applies to either figure — both are independent, manually entered observations with no transaction or category association, so those flags must not gate whether a recorded amount counts toward net worth or display.
- **Null semantics:** A property with **no** security-deposit observation on record must resolve to `null`, not `0`, and render as "—" — identical to `PropertyEquity.value`'s existing "never valued ⇒ null, not zero" rule in `lib/domain/property.ts`. The identical rule applies to last-month-rent-held. An explicitly recorded `$0` (a waived deposit; a last-month holding fully applied and not yet re-collected) is a real reading distinct from "never entered," and must render as `$0`. The underlying data must let a caller distinguish "no row exists for this property" from "a row exists with value 0" *before* formatting — the same distinction `latestValueByKey`'s `Map.has(key)` already makes, and the newest-per-property reduction for these two new series must reuse that "newest by `valued_at`, not last-row-wins" rule rather than a second, independently written reducer.

## Failure modes to test
- The security deposit is subtracted from the trust-checking account's own ledger balance (double-counting against `operational`/`capitalFinancial`, which already carries that cash at full value) instead of being an independent reduction to `liabilities`.
- Last-month-rent-held is wired into the same code path as the security deposit, so it also reduces `liabilities`/`total` — directly contradicts the owner's already-made decision.
- A missing observation (never entered) is defaulted to `0` instead of `null` for either figure — the exact regression this item exists to prevent.
- A deposit reduces `liabilities`/`total` without emitting a matching `NetWorthContribution` — `/net-worth`'s per-line breakdown for "Other debt" then does not sum to the card's own headline figure, an unexplained discrepancy on the one page whose entire job is explaining the decomposition.
- A deposit's contribution is emitted with a non-null `propertyId`, breaking the documented invariant that the field is exclusive to `realEstateEquity`, or is emitted with `kind: 'account'` instead of `kind: 'property'`, causing `app/net-worth/page.tsx`'s existing generic name/href resolution to look the entity up in the wrong table.
- **A security deposit is dropped for a property that also appears in `unvaluedPropertyIds`,** by reusing the mortgage's "drop the pair together" exclusion logic uncritically instead of treating the deposit as independent of valuation status — understates `liabilities` by the deposit amount for any rental that simply hasn't been revalued this quarter, silently, and only on the subset of properties missing a fresh valuation.
- **The `liabilities` component's `hint` is left unedited** (`'Loans not secured against a property'`), so a security deposit renders under a caption that both misclassifies it as a loan and denies its association with a specific property — a correct number under a false description.
- A property-linked mortgage at the same property as a deposit gets double-subtracted, e.g. by naively summing "everything liability-shaped for this property" instead of keeping the mortgage's existing `realEstateEquity` treatment and the deposit's new `liabilities` treatment separate.
- `operational + capitalFinancial + realEstateEquity + liabilities === total` breaks because the deposit reduction is applied to `total` directly (or in a fifth, uncounted place) rather than folded into `liabilities` before the four are summed.
- `lib/domain/propertyLedger.ts`'s running/ending balance is modified to "net out" the deposit, breaking bank-statement reconciliation — the ledger's sole stated job.
- `lib/domain/propertyPnl.ts` is modified to specially classify a security-deposit-received transaction, when this task explicitly scopes out any P&L change.
- The "latest observation per property" reduction for the two new series is written independently (e.g. last-row-wins) instead of reusing `latestValueByKey`'s newest-by-`valued_at` rule — works by accident until a query loses its `ORDER BY`, then silently reports a stale figure as current, the exact defect class `lib/domain/property.ts`'s header comment already documents fixing once.
- `net_worth_snapshots` rows written before this feature shipped are treated as if they already reflect deposit-adjusted `liabilities` (e.g. a "change since first snapshot" delta on the dashboard computed against a stale-definition baseline) — a silent trend-chart discontinuity.
- A `type = 'primary'` property is special-cased or rejected at the **domain-function** level. Nothing in `computeNetWorthBreakdown`'s or `computePropertyEquity`'s pure logic should branch on `properties.type`; the rental-only restriction belongs solely to the UI's data-entry affordance.
- Float drift from combining a string-sourced `NUMERIC` deposit value with the rest of the total without going through the same cent-rounded path everything else in `computeNetWorthBreakdown` uses.
- The `/properties` summary list is silently extended with either figure despite the explicit non-goal, or the `type='primary'` affordance restriction is silently skipped, or the `app/net-worth/page.tsx` edit spreads beyond the one authorized `hint`/`label` change (e.g. the `href` is also changed, or the generic contribution-mapping logic is touched).
