## Goal
Today the household's loyalty accounts (airline miles, hotel points and free nights, a card's transferable points, travel-agency cash, a car maker's points) live in a spreadsheet outside b8. After this change b8 holds them in a domain of its own, separate from the ledger. There are household members (a person who may or may not be a b8 user), a catalog of programs (each with a set of aliases, the names a program is known by), memberships (member × program, with a member number and a tier), append-only balance observations (as-of date, balance, unit, source) and instruments (certificates, companion fares, travel credits, each with issued, expires and used dates). A new page `/travel`, labelled "Nights & Miles", sits in the sidebar after Properties and before Gifts. It shows one card per program that has at least one membership, and one line per membership: member, current balance with its unit, tier, as-of date, a source badge, and a masked member number with a copy action. Below the cards it lists instruments sorted by expiry. Every field can be edited in place, and an edited balance is a new observation with source `typed`, never an update. The current balance of a membership is derived, never stored: it is the newest observation by as-of date, ties broken deterministically, and a membership with no observation shows no balance (not zero). Member numbers are stored in full but every response, page and log line carries them masked, with one exception: a single route that returns one membership's full number for the copy action to a signed-in browser session. A local script, run once on the home server against the owner's spreadsheet export exactly as the owner has it (the owner will not reshape it), imports the memberships, balances and bonus instruments. The sheet has a row label (a program name optionally followed by a household member's first name) instead of separate member and program columns, so the script resolves each label deterministically against the household's members and the programs' aliases, and refuses a row it cannot resolve exactly. It is a dry run unless `--apply` is given, it is idempotent, it is all-or-nothing, and it prints counts and row numbers only, never a name, number or balance. Nothing here reads email, Plaid or screenshots, and nothing here changes `accounts`, `account_valuations` or `computeCurrentNetWorth()`.

## Non-goals

Points, miles, nights and loyalty cash are never summed into any figure and never given a cents-per-point value. No loyalty figure appears on `/net-worth`, `/accounts`, `/dashboard`, the digest or in any push.
- **No later-step features (42b to 42h).** No card-fee detection, no earn estimate, no email inbox or IMAP, no screenshot capture, no stays, segments or redemptions, no transfers between programs, no expiry rules or alerts, no "Needs attention" section, no dashboard card, no digest widget, no push, no chat-agent tool. - **Columns reserved for later steps do not exist yet** (Open question 4). No sender domains, no expiry rule or inactivity months, no mailbox address, no qualifying-figures JSON, no source reference, no confirmation code. The one forward-looking column is the nullable `card_account_id` on memberships (a foreign key to `accounts(id)`, `ON DELETE SET NULL`). It is always null in this task: no route, form or import path sets or emits it, and no `accounts` row changes.
- **No annual-fee figure is stored, parsed, validated or printed anywhere.** The sheet's annual-fee column is not read for meaning at all: a malformed fee cell never refuses a row. No column, API field, page element or log line holds it (42b derives it from the ledger).
- **No update or delete of an observation, anywhere.** No route, store function or script issues `UPDATE loyalty_observations` or `DELETE FROM loyalty_observations`. A correction is a new, newer observation. No delete route exists for members, programs, memberships or instruments either (out of scope; the owner can ask later).
- **No second "current value" reducer.** The newest-wins selection goes through `lib/domain/observations.ts`. No other file reimplements "pick the newest row", and `latestValueByKey`'s existing behaviour and tests are unchanged.
- **No client-chosen observation source.** A route accepts only `typed` from a client. The values `import`, `email` and `screenshot` are never accepted from a request body.
- **The import never creates a program, an alias or a member, never updates an existing membership, observation or instrument, and never guesses a match.** No fuzzy, prefix, substring, edit-distance or "closest" matching of a label to a program or a member. A label resolves by exact equality after the stated normalisation, or the row is refused.
- **The import does not require the owner to reshape the sheet.** It does not require a `member`, `program`, `unit` or `as_of` column, and it does not require the header cells to match case or spacing exactly.
- **No full member number in any list, page, page prop, flight payload, error body, log line, import stdout or stderr.** The single exception is the one route in Surface table row S6.
- **No change to gifts, receipts, sync, push, the service worker, the scheduler, `proxy.ts`, or any existing migration.** Existing tests are only added to, never weakened.
- **No new dependency** and no network, Plaid, Anthropic or mail call from the import script or the new routes. The import script does not import `scripts/plaid-script-shared.ts` (it pulls the Plaid client types); it carries its own small usage-error type.
- **No real program balance, member number, member name, program label or fee** in any tracked file, comment, fixture, test or commit message. Fixtures are fabricated and use the canary prefix `ZQ42A`. The catalog migration contains program names and aliases only (public facts about the programs, per LOYALTY-ROADMAP §7), and the aliases are the programs' public names, never the household's labels.
- **No restyle of other pages.** UI work is the new page, its components, and the one Sidebar entry.

## Open questions for the owner
The owner accepted the defaults of questions 1, 2, 4, 5, 6, 7, 8, 9 and 10 on 2026-11-19; question 3 was replaced by the owner's availability rule below. Questions 11 to 13 are new decisions this revision made and the orchestrator should confirm; each states its default. The spec is written assuming all of them.
1. **Program catalog (accepted, with aliases added).** The migration seeds a catalog of at least 40 well-known programs (airlines at least 20, hotels at least 10, card currencies at least 5, travel-agency cash at least 1, car makers at least 3), deliberately wider than the household's 19, so the migration does not fingerprint the household. `/travel` can also create a program. The import never creates one. Because the sheet names programs by free-text label, every program also carries **aliases**: the stored, already-normalised names it is known by, unique across all programs (a database `UNIQUE` constraint, so an alias can never name two programs). The migration seeds, for every catalog program, at least its own name; for airlines and hotels, the brand alone and the brand plus the generic word that applies (`airlines`, `airways`, `hotels`), including the plain `airlines` form for carriers whose legal name is two words; the program's other current names, including recent rebrands; and for a card currency, the name of the flagship co-branded card. Aliases are editable through the program PATCH route. Reasoning: a label like "<brand> airlines <name>" cannot be matched by exact equality against one canonical program name, and fuzzy matching is forbidden, so the tolerated spellings are data the owner can see and fix, not logic. The orchestrator verifies locally, outside the repo, that the owner's real labels all resolve; that verification is never committed.
2. **Member-number mask (accepted).** The emitted mask is the literal four bullet characters `••••` (U+2022, always exactly four) followed by a suffix of the stored number, after trimming. Suffix length: 4 characters when the number has 8 or more characters, 3 when it has 6 or 7, none when it has 5 or fewer. A null or empty number emits null.
3. **Availability to instrument (the owner's rule).** An instrument is created if and only if the annual-bonus cell, trimmed, is non-empty and is not `-`, and the availability cell, trimmed and case-folded, is exactly one of `yes`, `available`, `issued`, `unused`. Any other availability (`no`, `-`, empty, `used`, `expired`, or any other text) creates none. A bonus cell that is non-empty and not `-` and creates nothing is counted once under `bonus_unplaced`. An instrument has kind `other`, description equal to the bonus text (at most 200 characters; longer refuses the row as a value error), `issued_on`, `expires_on` and `used_on` null, source `import`. The row's membership and balance still import either way.
4. **Later-step columns (accepted).** Only `card_account_id` (nullable, unused). The alias table is not a later-step column: the import needs it now.
5. **Unit vocabulary (accepted).** `points`, `miles`, `nights` (whole numbers, non-negative) and `usd` (money, non-negative, scale 2). A program carries a `default_unit`.
6. **Import source (accepted).** Imported observations carry source `import`, badge "imported".
7. **Import atomicity (accepted).** All-or-nothing: any refused row means `--apply` writes nothing and the exit code is 1.
8. **Future as-of dates (accepted).** An as-of more than one day after Postgres's `CURRENT_DATE` is refused (400).
9. **Full member number (accepted).** Cookie session only: a session of kind `browser`. Any bearer token (kind `personal`), whatever its scope, is refused.
10. **Uniqueness (accepted).** One membership per (member, program); a duplicate is 409, not 500.
11. **A `-` in the account-number cell is treated as empty (null member number).** Default: yes. The sheet uses `-` as a placeholder in its fee, bonus and availability columns, so the same placeholder in the account column is read as "no number", never stored as the number `-`. Alternative: store it. A member number of one dash is never real, so the default cannot lose data.
12. **Fully blank sheet rows are skipped silently and not counted in `rows`,** but they still take a row number, so the row numbers the script prints match the sheet. Default: yes. A row with any non-blank cell is a row.
13. **The default member.** A label whose last word names no household member needs `--default-member <name>`, which must resolve (trim, case-insensitive, whole display name) to an existing member. The default is never assumed from the first member, the owner or the first row. A row needing it when the argument is absent or does not resolve is refused as a member refusal. Members are never created by the import. Reasoning: the sheet has unsuffixed labels that belong to one person (the owner), and guessing who would be a silent mis-attribution.

## Conventions this task must honor
- **Sign.** Every balance is non-negative: zero is a legal, real reading (distinct from no reading) and a negative balance is refused by the API, by the import and by a database CHECK. There is no relationship to the ledger's sign convention (positive is money out), and nothing here is a ledger amount. A cash-denominated balance (`usd`) is a positive stored credit, never a liability, and is never negated, normalised or absolute-valued.
- **Units belong to the balance.** Vocabulary: `points`, `miles`, `nights`, `usd`. Each observation carries its own unit. A unit outside the vocabulary is refused (400 from the API, CHECK in the database). **API rules:** whole-number units accept only a string of 1 to 12 digits, with no sign, no fraction, no thousands separators and no decimal point at all (`"1500.0"` is refused). `usd` accepts 1 to 12 integer digits and optionally a decimal point with 1 or 2 fractional digits; a third fractional digit is refused. A balance of an integer unit is emitted with no decimal point, and a `usd` balance is always emitted with exactly two decimals, as decimal text and never as a JSON number. **Import rules (the import only, never the API):** the cell is first trimmed. If it is empty or exactly `-`, there is no observation. If it begins with `$`, the unit is `usd` and the `$` is removed; otherwise the unit is the matched program's `default_unit`. Then thousands separators are removed only when the digits before the decimal point are in groups of three with a comma between groups (`16,488` and `2,031.50` are accepted; `1,23`, `,500`, `1,5000` and `12,34,567` are refused as values). The remaining text must pass the API rule for that unit unchanged, so `31207.5` for a whole-number unit and `48.175` for `usd` are refused as values.
- **Rounding.** None, anywhere. Balances travel and compare as decimal text or SQL `NUMERIC`, by exact equality. No `Number`, `parseFloat`, `toFixed`, `Math.round` or multiplication by 100 on a balance, in any loyalty file. Excess precision is rejected, never rounded. The newest-wins reducer returns the winning row's balance text unchanged.
- **Current balance is derived.** For a membership with observations, the current balance is the observation with the greatest `as_of`; ties on `as_of` are broken by greatest `recorded_at`, then by greatest `id`. The result is identical for any ordering of the input rows. It is never "newest by arrival" (an older reading inserted later does not win) and never a stored column. An older reading that arrives later is still stored (append-only) but does not change the current balance.
- **Null semantics.** A membership with no observation has a null current balance, null unit, null as-of and null source, and the page renders "—" for it, never `0`. A balance of exactly zero is a reading and renders as `0` with its unit. A blank or `-` balance cell in the import produces no observation (counted under `observations_skipped_empty`), never a zero one. A null or empty member number emits null (no mask). A null tier emits null.
- **Label normalisation (one pure function, used by the import for labels and by the alias store for aliases and for program creation).** In this order: trim; drop leading characters that are not Unicode letters or digits (emoji, symbols, punctuation; matched with Unicode property escapes, never by code-unit ranges, so an emoji written as a surrogate pair is dropped whole); remove every parenthesised group (an opening parenthesis through the next closing parenthesis, and an unclosed opening parenthesis is left as it is); case-fold; collapse every run of whitespace (including non-breaking spaces) to one space; trim again. A label or alias that is empty after normalisation is refused.
- **How the import resolves a label.** (1) Member: the normalised label's final word or words, as a whole-word suffix, equal a household member's display name normalised the same way. If exactly one member's name is such a suffix, that member is the row's member and the rest of the label (re-trimmed) is the program label. If two or more members' names are suffixes of the label, the row is refused as a member refusal (ambiguous). If none is, the member is the one named by `--default-member` and the whole label is the program label. A label that is only a member's name leaves an empty program label and is refused as a program refusal. (2) Program: the program label must equal exactly one alias of exactly one program, by exact string equality. Zero matches refuses the row as a program refusal; the `UNIQUE` constraint makes more than one match impossible, and the code must still treat it as a refusal rather than pick one. (3) Duplicate: if two rows of the file resolve to the same (member, program), the second and every later one is refused as a duplicate. Rows are classified independently, so one run reports every refused row, not only the first.
- **Which columns the import reads.** Headers are matched after trimming, case-folding and collapsing whitespace, and a leading byte-order mark is ignored. The label column is the first column, and its normalised header must be empty (the sheet leaves it unnamed); otherwise the file is refused. The recognised headers are `balance`, `annual fee`, `annual bonus`, `annual bonus availability` and `account #`. `balance` is required. The others are optional, and an absent one reads as empty on every row. A recognised header appearing twice, a missing `balance` or a first column with a non-empty header refuses the file. Every other column is ignored. These file-level refusals exit 2, with a message that carries no data. `annual fee` is recognised only so that it is never mistaken for another column; its cells are never read.
- **Row numbers.** A "row number" in any output is the 1-based position of the row after the header, counting fully blank rows, so that it equals the spreadsheet's own row number minus one when the header is the sheet's first row.
- **Dates.** As-of, issued, expires and used dates are calendar `DATE`s with no time zone. The page's default as-of date for a typed balance is the browser's local calendar date through `lib/localDate.ts`'s `localIsoDate` (never `toISOString().slice(0, 10)`), and the client sends it explicitly. The API requires an as-of date on every observation and refuses one more than one day after Postgres's `CURRENT_DATE`. The import takes the as-of date from a required `--as-of YYYY-MM-DD` argument for every row (the sheet has no date column); it never reads the wall clock. No loyalty file uses `new Date(`, `Date.now(` or `toISOString` outside `lib/localDate.ts`'s existing helper.
- **Instruments.** `expires_on` before `issued_on`, or `used_on` before `issued_on`, is refused when both are set. Any date may be null (unknown). Sort order for the page's list: unused instruments before used ones, then `expires_on` ascending with null last, then `id` ascending.
- **Landscape and exclusions.** Not applicable, and stated so the omission is deliberate: loyalty rows are not ledger rows, are not budget-, P&L- or landscape-scoped, and `hidden`, `exclude_from_budget` and `track_transactions` are never consulted. No loyalty query reads `transactions`.
- **Who may read and write, and how a handler learns it (read from the code).** The boundary `proxy.ts` calls `authorize(request)` from `lib/requestAuth.ts` on every request: 401 `UNAUTHENTICATED` when there is no valid credential, and 403 `INSUFFICIENT_SCOPE` when a `read`-scope session attempts anything but GET, HEAD or OPTIONS (`scopePermits` in `lib/bearerAuth.ts`; the only read-safe POST is `/api/v1/chat`). A handler learns who is calling from `credentialFrom(request)` in `lib/requestAuth.ts`, which returns an `ActiveSession` with `userId`, `kind` and `scope` (or null, which the handler answers as 401). A cookie carries only a session of kind `browser`; an `Authorization: Bearer` header carries only kind `personal` (`kindAllowedFor` in `lib/bearerAuth.ts`), with scope `full` or `read`; a bearer token can reach `/api/` paths only. The gift routes' shared helper `app/api/v1/gifts/giftResponses.ts` imports `authorize` and is the precedent. Rules: both b8 users (peers) see and edit everything, with no filtering by `userId`. A household member with no `user_id` has no access, and no route identifies a caller by a member id. Every write route must itself refuse a `read`-scope session with 403 `INSUFFICIENT_SCOPE` and change nothing (it must not rely on the boundary alone, because the route tests call handlers). GET routes are open to a read-scope token and return masked data only. The full-number route (S6) answers 403 to any session whose `kind` is not `browser`, whatever its scope, and the body of that 403 carries no number.
- **Member-number handling.** Stored trimmed, in full. Emitted masked by the Open question 2 rule on every response except S6. Never in a log line, an error body (a refused request must not echo the submitted number), a page prop, the import's stdout or stderr, or a push. The copy action fetches S6 on click only, never on page load.
- **Import output.** Exactly the 20 lines listed in command 9 (a `mode` line, 14 count lines and 5 row-number lines), each matching `^[a-z_]+=([0-9]+(,[0-9]+)*|dry-run|apply)?$`. The row-number lines list row numbers only (for example `refused_rows_program=2,17`) and are empty after the `=` when none. The script writes its output through a `deps.out` function and its errors through `deps.err`, after the pattern of `scripts/rekey-plaid-ids.ts`; nothing else writes to stdout or stderr. Exit codes: 0 success, 1 any refused row or conflict, 2 usage or file-level refusal.
- **Process requirements for the implementer.** Read the relevant guides under `node_modules/next/dist/docs/` (resolved from `apps/web`) before writing any Next-facing code (page, route handlers, client components); this Next.js has breaking changes. Invoke the `uiux-promax` skill before building the page and its components (tokens, palette, list layout, phone layout). The installed PWA on a phone is a primary target. Record in EVIDENCE.md which docs files were read.
- **No money-looking figure in any tracked file's prose, comment or commit message** (AGENTS.md rule). Fixture CSV cells are the only place balances appear, and they are fabricated.

Before running it on the real database, back up the six tables with `pg_dump` (the owner runs it; reads are allowed, writes go through the owner's own command), or export the data you want to keep; the original spreadsheet is the source for the imported data and the one-time import can be re-run after a re-apply of the migration, because it is idempotent (members must be re-created first, since the import never creates them). Typed edits made on `/travel` after the import exist only in the database and must be backed up if they matter. After the revert the sidebar entry, the page and the 11 routes disappear, `ROUTES` and `PAGES` lose their entries together with the files (W4 stays green), the surface script returns to ending in `OK H1-H10`, and `latestValueByKey` and every ledger, net-worth, gift and receipt behaviour is unchanged. The contract change is additive, so nothing consumes the removed schemas after a revert.
