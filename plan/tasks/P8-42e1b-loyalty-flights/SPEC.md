## Goal
Every flight booking, change and cancellation that reaches the loyalty inbox from an airline program is read once by Claude in a third, separate read (the flight read) that extracts only: which kind of flight mail it is, the program's frequent-flyer-number suffix as printed, the confirmation code, whether the itinerary printed is the complete one, whether it was paid with an award, and per segment the departure date, origin and destination airport codes, carrier code and flight number. A cleaned booking becomes segments on the right membership, or is held for one tap when it cannot be placed with confidence. A later mail for the same program and confirmation code updates its segments; a cancellation marks them cancelled and never deletes them; mail never revives a cancelled segment. `/travel` shows, in a new `Flights` section, the upcoming flights and the recent completed ones with the confirmation code masked, the held bookings with one-tap choices, and a typed way to add or correct a segment. No flight count, mileage or status-credit figure is computed anywhere. The balance read, the hotel booking read, auto-apply, queue, retry, lock, retention, the screenshot path and the `Hotel stays` section are unchanged.

### Findings that shape this spec (read from the code at HEAD)
- 42e1's booking read reads **only messages whose program has kind `hotel`** (`CANDIDATE_SQL` in `lib/loyaltyBookingRead.ts`; T42e1-I1 asserts an airline-kind message is never booking-read). So airline-program mail never reached 42e1, and the only rows 42e1 can have left in state `flight` are messages of **hotel** programs that the model classified as flights. A segment must sit on a membership of an airline program, so those rows cannot be attributed to one.
- 42c1 does not blank the bytes of old mail: `purgeExpiredInbox` **deletes the whole message row** once `received_on` is older than `LOYALTY_INBOX_RETENTION_DAYS` (30). Booking-read and flight-read rows are purged later, at `LOYALTY_READ_RETENTION_DAYS` (400). A message that no longer exists can never be read; there is no row to reset.
- 42e1's held-booking table `loyalty_inbox_booking_reads` forbids what a flight needs: its `kind` CHECK lacks the flight kinds, its `flight_state` CHECK says state `flight` holds nothing, its `recorded_has_stay` CHECK demands a stay, its `booking` JSON shape is hotel-only, and its `dedupe_key` is UNIQUE so a legacy `flight` row cannot move to another state without a new meaning for an old row. Sharing it would alter four existing CHECKs on a table with live rows.

### Decisions the item delegated to this spec
Each is binding; the short reason is for the reviewer.

**D1 — Which mail the flight read reads, and what happens to rows 42e1 left in `flight`.** The flight read's candidates are stored messages with bytes whose program has kind `airline`, with no flight-read ledger row or one in `retry`, oldest received first, at most `LOYALTY_READ_MAX_PER_RUN`. Mail of every other program kind (hotel, card currency, travel cash, car, other) is never sent to the flight read. Rows 42e1 left in state `flight` belong to hotel programs; **they are not read, reset, updated or deleted by this task**, and a test proves a hotel-program message with such a row and bytes is never given to the flight reader and its row is byte-identical afterwards. *Why:* a segment needs an airline membership; a hotel program's mail names none; resetting a row to `retry` would make 42e1's booking pass read it again (a second paid read of the same message for the same purpose) and 42e1's code and tests are frozen. Residual stated: a flight confirmation that comes from a booking site or travel agency (a program that is not of kind `airline`) is not read.

**D2 — A third read, not a wider schema.** `BOOKING_SCHEMA`, `BOOKING_SYSTEM_PROMPT`, `READ_SCHEMA`, `READ_SYSTEM_PROMPT`, `createBookingReader` and `createMailReader` are unchanged. New `FLIGHT_SCHEMA`, `FLIGHT_SYSTEM_PROMPT` and `createFlightReader` are added to `apps/web/lib/loyaltyReader.ts` (additions only; it stays the only SDK importer). *Why:* the hotel read is pinned by 42e1's tests; a nested array of legs in the hotel schema would change what every hotel read asks and its cost. Cost: one model call per stored airline-program message, stated and accepted (including marketing and statement mail from the airline, which the model answers with kind `none`).

**D3 — "Read once": a ledger of its own, never a second paid read of any message.** A new table `loyalty_inbox_flight_reads`, keyed by the message's `dedupe_key`, records every message the flight read attempted. A message with a settled ledger row (any state but `retry`) is never given to the flight reader again; a `retry` row is read again until `LOYALTY_READ_MAX_ATTEMPTS`. Nothing in `loyalty_inbox_reads`, `loyalty_observations`, `loyalty_inbox_booking_reads` or `loyalty_stays` is read or written by the flight pass. The first run after deployment reads every airline-program message still held (at most thirty days of mail), at most `LOYALTY_READ_MAX_PER_RUN` per run, oldest first; the rest wait for the next run. *Why:* the airline mail of today is the only mail that can be read; older mail no longer exists (42c1 deletes it), which is stated, not worked around.

**D4 — Separate run, lock and daily step.** `lib/loyaltyFlightRead.ts` exports `readStoredFlights(env?)` (resolves, never rejects), `purgeExpiredFlightReads(q?)`, `runLoyaltyFlightsDaily()` and `resolveFlight(id, body)`. The pass takes its own advisory lock (key text `b8:loyalty-flights:read`, distinct from the poll's, the balance read's and the booking read's). `scheduler.ts` imports and calls `runLoyaltyFlightsDaily()` directly after `runLoyaltyBookingsDaily()` and before the digest. `readStoredMail`, `runLoyaltyReadDaily`, `readStoredBookings` and `runLoyaltyBookingsDaily` are not edited. There is no on-demand route. *Why:* the existing tests count connections and mock only the readers they know.

**D5 — Retry, failure and bounds mirror 42c2 and 42e1.** At most `LOYALTY_READ_MAX_ATTEMPTS` attempts; the attempt is committed before the model is called; `refused` and `empty_message` are terminal at once; a rate limit stops the run; `LOYALTY_READ_STOP_AFTER` consecutive `timeout` or `api_error` results stop it; `LOYALTY_READ_RUN_BUDGET_SECONDS` starts no new message; one call is bounded by the reader timeout plus five seconds. With no `ANTHROPIC_API_KEY` the run is `disabled` and writes nothing. Flight-read rows are purged by `received_on` strictly older than `LOYALTY_READ_RETENTION_DAYS` days, held ones included, by `runLoyaltyFlightsDaily` (the purge runs even when reading is disabled); **segments are never purged or deleted by anything.**

**D6 — The clean pass: all or nothing, bounded, never the model's word.** From the model's answer only these are kept: the kind (`flight_booked`, `flight_cancelled`, `none`), the cleaned suffix (42c2's `keepSuffix`), the program name in comparison form (42c2's `programNameForm`, check-only), the confirmation code (42e1's `normaliseConfirmationCode`: letters and digits, upper-case, 4 to 20), the award flag (only the booleans), a `complete` flag (true only for the boolean true, else false), and the legs. A leg is `{ flightDate, origin, destination, carrier, flightNumber }`: `flightDate` a real calendar date (42c2's `isCalendarDate`); `origin` and `destination` three letters A to Z after trimming and upper-casing, and different from each other; `carrier` two characters A to Z or 0 to 9 after trimming and upper-casing; `flightNumber` one to four digits optionally followed by one letter A to Z, after removing spaces and upper-casing, leading zeros kept. **If any leg is invalid, the whole leg list is void** (the booking then carries `legsVoid` true and no legs): a partial itinerary is never kept, because with a complete-itinerary flag a missing leg would cancel a real one. More than `LOYALTY_SEGMENTS_MAX_PER_MAIL` (12) legs is void. Legs repeating one identity (D7) within a mail count once. A booked mail with no code, no legs or void legs is state `no_booking`, stored as nothing. A cancellation with void legs is `no_booking` (never widened into a whole-booking cancel); a cancellation with no legs listed and no void flag cancels the whole code (D7). A mail whose legs are not all within `LOYALTY_SEGMENT_PLAUSIBLE_DAYS` (366) days before or after its received date (integer day arithmetic, both ends inclusive) is `no_booking`: the model mis-dated it. Typed legs are not subject to that window. Other keys the model returns (passenger name, ticket number, seat, cabin, fare, price, times, card digits, frequent-flyer number) are never looked at.

**D7 — Segment identity across mails for one code: the leg, and the itinerary only when the mail says it is whole.** A segment (leg) is identified by program, normalised confirmation code, flight date, carrier and flight number; origin, destination and award are attributes that a later mail updates. A mail that **applies** (D8) acts on the legs of its code as follows, and rows are never deleted:
1. `flight_booked`: each listed leg whose row is **booked** is rewritten (origin, destination, award, source `email`, evidence this mail); each listed leg whose row is **cancelled** is left unchanged (mail never revives, A5), unless the action is by hand (`place`, D10); each listed leg with no row is inserted `booked`, on the membership the code's existing rows are on, or the placed membership when none exist.
2. If the mail's `complete` flag is true, every **booked row of that code with source `email`** whose identity is not among the listed legs becomes `cancelled` (evidence this mail): the itinerary was replaced. Rows with source `typed` are never cancelled by omission. If `complete` is false, nothing omitted changes.
3. `flight_cancelled` with listed legs: each matching row becomes `cancelled`; a listed leg with no row is inserted `cancelled` (so a late confirmation of it is recognised); other legs of the code are untouched.
4. `flight_cancelled` with no legs listed: every booked row of the code becomes `cancelled`; a code with no rows stores nothing (`no_booking`).
5. The outcome is `recorded` when at least one row was inserted, rewritten or cancelled, and `stale` when the mail applies by D8 yet changes nothing.
All rows of one code are on one membership (the first attribution is sticky); the ledger row records that membership. *Why:* matching on date and number alone leaves a ghost leg when a change moves a flight; replacing the whole itinerary on every booked mail would cancel real legs when a reminder lists only one flight, so replacement is gated on the model saying the listing is complete, which is false by default; a typed leg is the person's word and a mail may not silently cancel it.

**D8 — Supersession is 42e1's D8 with A5, applied to the code as a group.** The standing of a code's group is: `cancelled` exactly when it has at least one row and every row is cancelled, else `booked`; its evidence date is the latest `evidence_received_on` over its rows (none when no row has evidence). A mail applies exactly when 42e1's `supersedes` rule says so for that standing: a `flight_booked` mail **never** applies to a wholly cancelled group unless by hand; with no evidence it applies; a strictly later received date applies; an equal date applies to a cancellation, and to a booking only when the group is booked; an earlier date does not. The rule is checked **before attribution**: a `flight_booked` mail whose code's group is wholly cancelled is `stale` at once and is never held (so a re-forward of an old confirmation cannot be placed by one tap; a cancelled flight is re-booked only by a typed write). A typed write rewrites its leg, sets source `typed`, and KEEPS that row's evidence date and key, so an older mail cannot undo a correction. *Why:* this is the rule 42e1 learned in review (arrival at the inbox is not event time); N6 of 42e1's NITS is avoided here by deciding stale before the hold.

**D9 — Attribution is 42e1's D9, imported.** Every flight mail that reaches the attribution step goes through `placeBooking` of `lib/domain/loyaltyBooking.ts` and 42c2's `programCheck` and `matchSuffix`: program mismatch holds `program_mismatch`; a unique suffix match places (a forwarder on a different membership holds `forwarder_conflict`); an unmatched suffix is discarded when `(program, suffix)` is on `loyalty_inbox_not_mine`, else held `unmatched_suffix`; an ambiguous suffix holds `ambiguous_suffix`; no suffix places on the forwarder's membership in this program, else holds `no_suffix`. Unlike 42e1's undated cancellation, **no flight mail bypasses attribution**: a cancellation that cannot be placed is held too. *Why:* one rule, no second place for the two reads to disagree about whose mail it is.

**D10 — The hold: same actions, own table, own route.** A held flight booking is a `pending` row of `loyalty_inbox_flight_reads` carrying its cleaned booking as a fixed-key JSON object (`kind`, `code`, `award`, `complete`, `legs`) until resolved, then the object is cleared. `POST /api/v1/loyalty/inbox/flights/[id]` takes the same body as 42e1's hold route (the existing `LoyaltyBookingResolveRequestSchema`) and answers `{ id, state }` (the existing `LoyaltyBookingResolveSchema`): `place` (membership must be of the item's program; applies the held booking by D7 and D8 **by hand**, so it may re-book a cancelled leg; state `placed_by_hand`), `not_mine` (records `(program, suffix)` in `loyalty_inbox_not_mine` idempotently and resolves every other pending flight item of that program and suffix to `not_mine`), `ignore`. A second action on a resolved item is 409 `ITEM_RESOLVED`; two simultaneous places make one set of segments; an unknown id is 404 `NOT_FOUND`. *Why (deviation from ITEM point 3, which said "joins 42e1's held-booking list"):* see "Deviations from the ITEM".

**D11 — What `/travel` shows, and what it never computes.** A new `Flights` section (own component, rendered after the `Hotel stays` section; that section's strings and order are unchanged). The payload `LoyaltyFlights` holds `airlineMembershipIds`, `upcoming`, `recent` and `queue` and nothing numeric beyond ids and dates. `upcoming`: booked segments whose flight date is on or after Postgres `CURRENT_DATE`, ordered by flight date then id. `recent`: booked segments whose flight date is before `CURRENT_DATE` and on or after `CURRENT_DATE` minus `LOYALTY_SEGMENT_RECENT_DAYS` (30), ordered by flight date descending then id. A cancelled segment is in no list. **No flight count, no mileage, no status credit, no per-airline total is computed, stored or shown**; the page says miles and status credits follow each airline program's own rules and are not calculated here. A flight dated today is upcoming for the whole of today (dates only; no time of day or time zone is stored).

**D12 — Typed fallback.** `POST /api/v1/loyalty/segments` with a strict body `{ membershipId, confirmationCode, flightDate, origin, destination, carrier, flightNumber, state, award }` (`award` boolean or null) creates a segment (201) or, when that membership already holds the same leg identity, rewrites it (200). The membership must be of a program of kind `airline` (else 400 `INVALID_INPUT`); an unknown membership is 404; a code recorded under another membership of the program is 400 with a fixed sentence echoing nothing. Origin, destination, carrier and flight number are accepted in either case, trimmed, and stored upper-case; they must then pass D6's shapes. `state` may be `booked` or `cancelled` (the only way to cancel by hand, and to re-book a cancelled leg); nothing deletes. A typed write sets source `typed` and keeps that row's evidence. Write scope required. To correct a wrong date or flight number a person adds the right segment and cancels the wrong one; there is no edit by id. *Why:* one dedupe rule.

**D13 — Masking and what is never stored.** The code is stored in full normalised form and every payload carries `maskedCode` produced by the same masking function member numbers use. No route returns a full code. Never stored, logged or returned: passenger names, ticket numbers, seat, cabin or fare class, frequent-flyer numbers beyond the 42c2 suffix, prices, taxes, card digits, times of day, addresses, phone numbers, mail text, model output. The only values from the mail that reach a column are listed in D6.

**D14 — Award flag.** `award` is true when the mail states a payment with miles or an award, false when it states cash, null when it states nothing; stored per segment, shown nowhere (42e2).

**D15 — Clock.** "Today" is Postgres `CURRENT_DATE`; the plausibility window and every date comparison are `YYYY-MM-DD` text order or integer day arithmetic through 42e1's `nightsBetween`; no JS clock, no `Date` object.

### Table design (binding; names are fixed so commands can check them)
**`loyalty_segments`** — columns, sorted: `award` BOOLEAN NULL; `carrier` TEXT NOT NULL CHECK `^[A-Z0-9]{2}$`; `confirmation_code` TEXT NOT NULL CHECK `^[A-Z0-9]{4,20}$`; `created_at` TIMESTAMPTZ NOT NULL DEFAULT NOW(); `destination` TEXT NOT NULL CHECK `^[A-Z]{3}$`; `evidence_key` TEXT NULL CHECK `^[0-9a-f]{64}$`; `evidence_received_on` DATE NULL; `flight_date` DATE NOT NULL; `flight_number` TEXT NOT NULL CHECK `^[0-9]{1,4}[A-Z]?$`; `id` SERIAL PK; `membership_id` INTEGER NOT NULL; `origin` TEXT NOT NULL CHECK `^[A-Z]{3}$`; `program_id` INTEGER NOT NULL REFERENCES loyalty_programs(id) (no ON DELETE); `source` TEXT NOT NULL CHECK in `typed`, `email`; `state` TEXT NOT NULL CHECK in `booked`, `cancelled`; `updated_at` TIMESTAMPTZ NOT NULL DEFAULT NOW(). Constraints: UNIQUE `(program_id, confirmation_code, flight_date, carrier, flight_number)`; CHECK `origin <> destination`; CHECK `(evidence_key IS NULL) = (evidence_received_on IS NULL)`; CHECK `source <> 'email' OR evidence_key IS NOT NULL`; composite FOREIGN KEY `(membership_id, program_id)` REFERENCES `loyalty_memberships (id, program_id)` (no ON DELETE). Index `(membership_id, flight_date)`. *Why:* the unique tuple is the identity of D7; the composite key stops a segment under a membership of another program; nothing cascades.

## Conventions this task must honor
- **Sign:** no ledger amount exists in this task. No price, tax, fare, mileage or balance is read, stored, computed or shown, so the ledger sign convention is not consulted. A segment's origin and destination are different airports.
- **Rounding:** none. No figure is computed. Date distances (the plausibility window) are integer day counts; no JS date arithmetic, no `Date`, no float.
- **Landscape and exclusions:** not applicable. No ledger row is read or written, so `landscape`, `hidden` and `exclude_from_budget` are never consulted; nothing feeds net worth or `computeNetWorth()`. `/travel` stays `numeric-only` (its overview derives a fee date from a ledger row); the two new routes are `no-transaction-data`.
- **Null semantics:** `award` null means not stated, never false. A section with no data renders its empty text (`No flights to show`), never a zero or a count; no key anywhere holds 0 for "nothing". A membership with no flights shows nothing for it.
- **Dates and clock:** "today" is Postgres `CURRENT_DATE`. None of `new Date(`, `Date.now(`, `toISOString`, `getTime(`, `setDate(`, `setHours(`, `getTimezoneOffset`, `toLocaleDateString`, `toLocaleTimeString`, `parseFloat`, `parseInt`, `toFixed`, `Math.round` appears in any added non-test line (command 16). A date is `YYYY-MM-DD` text, validated by `isCalendarDate`, ordered by string comparison.
- **Identifiers:** the confirmation code is an identifier: stored in full, masked everywhere, never in a log, push, mail, agent context or API payload. The frequent-flyer suffix is the 42c2 fragment (at most four characters), masked in payloads.
- **Determinism:** no live Anthropic, Plaid or mailbox, no non-loopback socket, no `b8_finance`; the model is faked by mocking `createFlightReader` or injecting a client; Postgres is the throwaway `b8_p42a_throwaway`; day arithmetic is Postgres `CURRENT_DATE` with offsets.
- **Cross-cutting source scans (named so a failure is read correctly):** several existing unit tests read every file under `components`, `app/travel`, `lib`, `lib/domain`, `app/api/v1` or `packages/contracts` (`loyaltyReadUi`, `loyaltyInboxUi`, `loyaltyCardUi`, `loyaltyEarnUi`, `loyaltyNits`, `findingsWiring`, `giftSurfaceWiring`, `enrichedDisplayWiring`). The only edit to any of them is the A3-style pin in command 15; any other failure they report is a G2 amendment, not a silent test edit.

The model is faked by mocking `createFlightReader` in `@/lib/loyaltyReader` (or injecting a client in reader unit tests); `createBookingReader` and `createMailReader` are mocked too, only to count: the flight pass must call neither. Raw answers are fabricated objects, including injected keys (`passengerName`, `ticketNumber`, `seat`, `address`, `phone`, `cardLast4`, `total`) and a full printed frequent-flyer number in the suffix field. A message is a fabricated RFC 822 text built in the test and stored with `INSERT INTO loyalty_inbox_messages`. Captured console lines are the whole file's, each a JSON line with `level`, `scope`, `message`. An airline program is `kind = 'airline'`; hotel, card and other-kind programs are seeded where the scenario says so.
