## Findings

### [NIT] apps/web/lib/loyaltyNits.test.ts:342-351 — U2 detects a call to the null handler only from the "Remove number" element
The spec's failure-mode list includes "A 'Cancel' or 'Keep' that sends the null PATCH". U2 catches that only when the literal `{ memberNumber: null }` is inlined in the Keep handler (fixture `secondNull`).

**Failure scenario:** change Keep to `onClick={() => removeNumber()}`. One tap on Remove followed by Keep then erases the number. U2 still passes: there is one null literal, its handler is attached to an element labelled Confirm, and the Remove element does not call it. Command 15 still counts one literal. Every acceptance command stays green. The current code is correct (Keep only resets state).

Follow-up: extend the call-through check from line 348 to every JSX `on…` handler in the file that is not the Confirm element, and add a fabricated `keepClick: '() => removeNumber()'` violation.

### [NIT] apps/web/lib/loyaltyNits.test.ts:336-352 — U2 does not prove Confirm appears only after the first tap
**Failure scenario:** render `<button onClick={removeNumber}>Confirm</button>` next to "Remove number", without the `confirmingRemove` branch. The user then has a one-tap destructive Confirm that is always visible, and U2 accepts the source. Spec rule (3) as written does not demand this, and limit (1) declares the checks AST-only, so this is not a spec breach. The current code nests Confirm under `confirmingRemove ? … : …` correctly, and the implementer's browser log confirms Confirm is hidden until Remove is tapped.

Follow-up: assert that the Confirm element sits in the `whenTrue` branch of a conditional whose `whenFalse` branch contains the Remove element.
