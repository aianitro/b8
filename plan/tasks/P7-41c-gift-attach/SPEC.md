# P7-41c-gift-attach — Attach an already-synced transaction to a waiting gift, and default "Expected from" to the giver's local today
**Roadmap item:** not a ROADMAP.md §5 step. A follow-up to P7-41b (ROADMAP.md §5 Phase 7 step 41b, `6472c64`) and its authorized-date fix (`e7c7232`). Origin and constraints: `plan/tasks/P7-41c-gift-attach/ITEM.md`. Source of the masking rules: `plan/tasks/P7-41b-gifts/SPEC.md` (with Amendments), `NITS.md`, `GATES.md`.
**Status:** FROZEN@G0 (2026-10-22)
**Author:** spec-writer

## Goal
Today a gift can only claim a row at the moment the Plaid sync first inserts it. A row that already sits in the ledger when its gift is created, or that missed the window, can never be linked, and the gift waits until it expires. After this change the giver, and only the giver, can look at a waiting gift and see the recent unlinked outflows that satisfy the gift's amount, merchant and account criteria while ignoring the window, and can pick one. The pick is linked exactly as the sync would have linked it: the row's prior category and `rule_applied` are recorded, the row is filed in the designated gift category with `rule_applied` false, the gift's state moves (`awaiting` to `matched`; `choose` stays `choose` with one more held candidate), and from that statement on the row is masked as `Gift` for every non-giver until the reveal date, with totals unchanged for every viewer. Two new routes carry this: `GET /api/v1/gifts/[id]/candidates` and `POST /api/v1/gifts/[id]/attach`. Both answer the recipient, a third user, and a request for a nonexistent id with the same 404, so nothing in them reveals that a gift exists. A gift that is revealed (including one whose reveal date has come but which the daily sweep has not yet expired), cancelled, matched or unmatched refuses both. Separately, the gift form on `/gifts` opens with "Expected from" set to the giver's local calendar date (and "Expected until" set to the same date, see Open question 4), so the obvious case cannot start a day late. This task also closes P7-41b NITS N7 (see Open question 3): a gift past its reveal date can no longer claim a row at sync before the sweep expires it.

## Non-goals
Each is enforced by the reviewer as a defect if present.
- **No migration, no `db/schema.sql` change.** The existing `gift_transactions` link (with `prior_mapped_category` and `prior_rule_applied`) already holds everything attach needs. No column records that a row was attached rather than synced; after the fact the two links are indistinguishable by design.
- **No retroactive gifts for anyone but the giver, and no automatic one.** Attach is an explicit giver action on one named gift and one named row. Sync's rule is unchanged: it still claims only rows it first inserted, still within the window (either posted or authorized date), and still never claims a stored row. There is no "mark this existing transaction as a gift" control on `/transactions` or any other page, and no endpoint that takes a transaction and finds its gift.
- **Exactly two new routes and no new page.** `GET /api/v1/gifts/[id]/candidates` and `POST /api/v1/gifts/[id]/attach`. No bulk attach, no detach/unlink route (release stays `cancel` and `choose`), no editing of criteria, no change to `POST /api/v1/gifts`, `GET /api/v1/gifts`, `GET /api/v1/gifts/[id]`, `choose`, `cancel`, and no change to `app/gifts/page.tsx`.
- **No new notification, no push change, no new timer.** Attaching sends nothing to anyone. `apps/web/public/sw.js`, `lib/domain/pushPing.ts`, `lib/webPush.ts`, `lib/scheduler.ts` and the digest are unchanged.
- **No second definition of "a row satisfies a gift".** The attach rule is the existing `isCandidate` rule minus the window; it is not a re-implementation. `isCandidate` itself and its callers' behaviour are unchanged.
- **`lib/sync.ts`, `lib/giftLock.ts`, `lib/giftReadPath.ts`, `lib/domain/giftMask.ts` are unchanged.** In `lib/giftStore.ts`, `linkFreshRows` changes in exactly one respect: the N7 conjunct (Open question 3). - **No change to what totals mean.** No new budget, landscape, category or exclusion semantics; no change to `hidden`, `exclude_from_budget`, `track_transactions` handling; the gift category is never designated, renamed or created by this task.
- **Attach does not touch fields other than the two it files.** It never changes a row's `hidden`, `note`, `watched_at`, `property_id`, `transfer_group_id`, `date`, `amount`, or any Plaid-sourced column.
- **No timezone conversion for gift windows.** Gift dates stay the server's Postgres calendar. Only the form's initial values use the giver's browser calendar (owner's instruction); no code converts between the two.

## Open questions for the owner
Each has a default; the spec is written assuming the defaults. A different answer changes the scenarios named.
1. **How far back do candidates go?** Default: a row is listed when its posted date is on or after (the gift's creation date on Postgres's calendar minus 7 days), with no upper bound, ignoring the gift's window entirely, newest first, at most 50 rows. Reasoning: the failure being fixed is "the row was already there, or dated just before, when I made the gift"; a creation-based floor keeps a long-waiting gift from losing older-but-relevant rows (a "last N days from today" rule would), while 7 days of grace covers a purchase bought a few days before the giver thought to mark it. Alternative: last N days from today. Scenarios C4, U5.
2. **Can a `choose` gift take an attach?** Default: yes. The row joins the held candidates (filed, masked), the state stays `choose`, and the giver resolves with the existing `choose`. Reasoning: the right row may be one the matcher never saw. Alternative: only `awaiting` gifts, so a giver with several wrong candidates must cancel and re-create. Scenario C2 inverts.
3. **Is N7 fixed here?** Default: yes. `linkFreshRows` stops offering rows to a gift whose reveal date has come, so sync and attach agree on "revealed means closed" and a late row cannot be re-filed into the gift category before the sweep. Alternative: leave N7 open and fix separately. Scenario C11 drops; attach's own refusal of revealed gifts (C7) stays either way.
4. **Form defaults.** Default: "Expected from" is the giver's local calendar date; "Expected until" is the same date (a one-day window), editable; "Reveal on" has no default. Alternatives: "Expected until" empty (forces a decision, cannot be forgotten and left too short) or from plus a fixed span. Scenarios U7, U8.
5. **Candidate list for an ineligible gift.** Default: `GET …/candidates` on the giver's own gift that is revealed, cancelled, matched or unmatched answers 409 `ALREADY_RESOLVED`, the same as attach does, rather than 200 with an empty list. Reasoning: an empty list would read as "nothing fits", which is wrong for a closed gift. Scenario C7.
6. **Rows inside a transfer pair.** Default: a row with a `transfer_group_id` is never a candidate and cannot be attached (fail closed; moving half of a transfer into the gift category would break the pair). Alternative: allow. Scenarios U3, C5.

## Conventions this task must honor
- **Sign.** `transactions.amount` follows Plaid: positive is money out on every account type including credit cards and loans; negative is money in or a refund (a deposit on checking, a payment row on a loan account). Only `amount > 0` rows can be candidates or attached. A refund of the gift's own magnitude, and a zero row, never qualify. Nothing is negated, normalised or absolute-valued. Amounts in every response are the stored `amount::text`, byte-identical.
- **Rounding.** None, anywhere. Amounts travel and compare as decimal text (or in SQL as `NUMERIC`), by exact equality. No `Number`, `parseFloat`, `toFixed`, `Math.round` or multiplication by 100 on an amount (cent parts such as the five listed in T41b-M3 break `×100` equality). The attach rule reuses the same comparison as `isCandidate`.
- **Landscape and exclusions.** Matching and attach ignore landscape, `hidden`, `track_transactions` and the account owner (accounts have none). A `hidden` row IS a candidate, and attaching it leaves `hidden` as stored. Attaching moves the row from its prior category into the designated gift category, so budget, pacing, year-end and net-worth figures move exactly as if the owner had filed that row there by hand, and no category flag is changed. Those figures are identical for the giver, the recipient and a third user, before and after the reveal date. A row that is a member of a transfer group is not a candidate (Open question 6).
- **Time.** Gift dates (window, reveal) and the candidate floor are calendar `DATE`s on Postgres's calendar (`CURRENT_DATE` under the server's configured zone). Eligibility ("not yet revealed") is `reveal_date > CURRENT_DATE` evaluated by Postgres in the statement that reads the gift: on the reveal date itself the gift refuses attach. Pure functions take `today` as a `YYYY-MM-DD` string argument and use string comparison and the integer calendar arithmetic of `addDays`. No file whose path contains `gift` (any case) uses `new Date(`, `Date.now(`, `toISOString`, `parseFloat`, `toFixed`, `Math.round` or multiplies an amount (T41b-W9 already enforces this on every gift-path file, new ones included). The form's "today" is the giver's browser calendar via `lib/localDate.ts`'s `localIsoDate` (not a gift-path file), never `toISOString().slice(0, 10)`.
- **Null semantics.** A gift criterion that is null means "any", never zero or empty string; a gift with neither amount nor merchant matches and attaches nothing. A candidate with no merchant name and no name is labelled `Unnamed` for the giver, and a merchant criterion never matches it. The candidate list is `[]` when nothing qualifies, never null. A masked field is absent or null for non-givers on every other surface exactly as P7-41b specifies; nothing here adds an exception.
- **Viewer and existence.** The giver is the signed-in user of the request, resolved by `authorize` as the other gift routes do. A gift that is not the viewer's answers exactly what a nonexistent id answers (same status, code, message, bytes after volatile fields), on both new routes, for the recipient, a third user and a malformed or unknown id. The 404 is decided before the body or the transaction id is looked at, so a non-giver sending a malformed body, or a real transaction id, still gets the 404. The candidate list is served only to the giver and is never rendered into any page's props, HTML or flight payload: it is fetched by the browser on the giver's click.
- **One refusal for "this row cannot be attached".** For the giver's own eligible gift, a transaction id that does not exist, is already linked to any gift (revealed or not, this gift or another), is a `manual_`/`csv_` row, is a refund or zero row, is in a transfer group, or fails the amount, merchant or account criterion, all answer the same 400 `INVALID_INPUT` with the same fixed message, which carries no row text, no criterion and no reason. The same holds if the row stopped qualifying between listing and attach.
- **Atomicity and concurrency.** Attach is one transaction: the link insert, the row's filing, and the gift's state change commit together or not at all. It re-checks the row's qualification and the gift's eligibility against the current committed data under locks, not against what the list showed. The primary key on `gift_transactions.transaction_id` means one link per row; attach must never answer 500 for losing a race, and must never deadlock with `runSync`, `chooseGift`, `cancelGift` or `runGiftSweep`.
- **Linking is the sync's link.** After attach, the link row, the row's `mapped_category`, `rule_applied` false, and the gift's state are indistinguishable from what `linkFreshRows` produces. If the gift category has been deleted since the gift was made, attach still links and masks the row, leaves its category, sets `rule_applied` false, and logs a count only (the same fallback as sync).
- **Logs.** Any log line from the new code carries counts only, no merchant, name, amount, note, label, criterion or row id (T41b-W8 enforces the word list on gift-path files).

## Rollback
Revert the commit. There is no migration and no schema change, so there is no `down` to run, no CSV backup to take, and no privacy event: rows attached while the change was live stay linked in `gift_transactions`, stay filed in the gift category and stay masked until their reveal date under the unchanged P7-41b code, because masking is keyed on the link and the reveal date, not on how the link was made. After a revert the giver loses the ability to attach (the two routes disappear and `/gifts` loses the control) and the form returns to empty date fields; gifts already matched keep working; `cancel` still restores an attached row exactly, since the prior values were recorded in the existing columns. The N7 fix is part of the same revert, which restores the pre-existing behaviour that a revealed-but-unswept gift can claim a row at sync. The contract file change is additive, so nothing consumes the removed schemas after the revert.
